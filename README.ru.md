# nocobase-multicore

Запуск **NocoBase 2.x (community) на нескольких ядрах процессора** — с переключателем в *Настройки → Многоядерный режим*.

NocoBase — это один процесс Node.js, то есть одно ядро процессора. Проект запускает его как **несколько процессов-воркеров на одном порту** и переносит всё, что должно быть общим между воркерами (события, блокировки, очереди, id записей, кэш), в Redis. Ядро NocoBase **не патчится**: всё сделано пятью обычными плагинами и небольшим лаунчером.

> Статус `0.1.0`, проверено на NocoBase **2.2.33** на тестовом стенде (см. [docs/TEST-REPORT.md](docs/TEST-REPORT.md)). Репозиторий приватный. ИИ-агентам, продолжающим работу: начните с [AGENTS.md](AGENTS.md).

## Что внутри

| Часть | Зачем |
|---|---|
| `supervisor` — лаунчер | Запускает N воркеров (`node:cluster`), плавно меняет их число, перезапускает упавшие. |
| `plugin-multicore` | Страница настроек: переключатель, число воркеров, таблица процессов, самопроверка кластера, страховка. |
| `plugin-pubsub-adapter-redis` | Общая шина событий между воркерами. |
| `plugin-lock-adapter-redis` | Блокировки между процессами. |
| `plugin-queue-adapter-redis` | Общая очередь задач (каждая задача — ровно одному воркеру). |
| `plugin-worker-id-allocator-redis` | Уникальные worker id, чтобы два процесса не создали записи с одинаковым id. |

Каждая часть подробно описана ниже (и в собственном `README` в `packages/<имя>/`). Когда режим выключен — или Redis не настроен — адаптеры ничего не меняют, и NocoBase работает как обычно в одном процессе.

## Как это работает

```
 браузер ─► :13000 ─► супервизор (главный процесс node:cluster, запросы не обслуживает)
                        ├─ worker 1  (полное приложение NocoBase)  ┐
                        ├─ worker 2  (полное приложение NocoBase)  ├─► PostgreSQL / MySQL  (общая база данных)
                        └─ worker N  (полное приложение NocoBase)  ┘
                                  │ pub/sub · блокировки · очередь · worker id · кэш
                                  ▼
                                Redis
```
1. Операционная система раздаёт входящие соединения воркерам по кругу.
2. Всё, что раньше жило в памяти единственного процесса, теперь в Redis — через штатные точки расширения самого NocoBase (`pubSubManager`, `lockManager`, `eventQueue`, `workerIdAllocator`, хранилище кэша).
3. Страница настроек пишет `storage/multicore/config.json`; супервизор читает его и делает **плавную замену** (новый воркер должен начать принимать запросы, прежде чем остановится старый) — простоя у пользователей нет.

## Требования

* NocoBase **2.x** community (проверено: `nocobase/nocobase:2.2.33`), Docker или локальный проект (`yarn nocobase ...`), Node.js ≥ 20.
* PostgreSQL или MySQL/MariaDB, общая для всех воркеров (та же, что уже использует NocoBase). *SQLite не подходит.*
* **Redis ≥ 6**, доступный как `REDIS_URL` (например `redis://redis:6379/0`), `maxmemory-policy noeviction`.
* Общая папка `storage/` (одна машина / один том).

## Установка

### Вариант A — одна команда (рекомендуется)

Скачайте архив `nocobase-multicore-bundle-0.1.0.tgz` из [`releases/v0.1.0`](https://github.com/rosaloverdue-dev/nocobase-multicore/tree/main/releases/v0.1.0) (или из GitHub Release), распакуйте и запустите:

```bash
tar xzf nocobase-multicore-bundle-0.1.0.tgz && cd nocobase-multicore-bundle-0.1.0

# NocoBase в Docker (укажите имя контейнера):
./install.sh --docker <имя-контейнера> --restart

# NocoBase из папки проекта:
./install.sh --local /путь/к/проекту-nocobase
```
Скрипт (идемпотентный — можно запускать повторно): копирует пять плагинов в `storage/plugins/@rosal-nb/`, супервизор — в `storage/multicore/supervisor/`, выполняет `pm add` и `pm enable` для каждого плагина. Опции: `--no-enable`, `--restart`, `--from <папка>`.

### Вариант B — загрузить TGZ-файлы в браузере

*Настройки → Менеджер плагинов → Добавить плагин → Загрузить*, по одному: `rosal-nb-plugin-pubsub-adapter-redis`, `…lock-adapter-redis`, `…queue-adapter-redis`, `…worker-id-allocator-redis`, `…plugin-multicore` (файлы `*.tgz` из папки релиза), затем **включите** каждый. Супервизор (это не плагин) всё равно нужно один раз скопировать — см. шаг 2 ниже. Загрузка/включение из интерфейса в работающем кластере затрагивает только процесс, принявший запрос, поэтому **после этого перезапустите контейнер**.

### Вариант C — ручные команды

```bash
# в контейнере NocoBase / папке проекта
for p in pubsub-adapter-redis lock-adapter-redis queue-adapter-redis worker-id-allocator-redis multicore; do
  mkdir -p storage/plugins/@rosal-nb/plugin-$p
  tar xzf rosal-nb-plugin-$p-0.1.0.tgz -C storage/plugins/@rosal-nb/plugin-$p
  yarn nocobase pm add @rosal-nb/plugin-$p
done
yarn nocobase pm enable @rosal-nb/plugin-pubsub-adapter-redis @rosal-nb/plugin-lock-adapter-redis \
  @rosal-nb/plugin-queue-adapter-redis @rosal-nb/plugin-worker-id-allocator-redis @rosal-nb/plugin-multicore
mkdir -p storage/multicore/supervisor && tar xzf nocobase-multicore-supervisor-0.1.0.tgz -C storage/multicore/supervisor
```

### Шаг 2 — запустить NocoBase через супервизор (один раз)

**Docker** — добавьте Redis и замените entrypoint контейнера (полный пример: `docker/docker-compose.example.yml`):
```yaml
services:
  app:
    image: nocobase/nocobase:2.2.33
    entrypoint: ["/bin/sh", "/app/nocobase/storage/multicore/supervisor/docker/entrypoint.sh"]
    environment:
      REDIS_URL: redis://redis:6379/0
      # за прокси / при другом имени хоста, если видите "Invalid sign-in origin":
      # CORS_ORIGIN_WHITELIST: "https://crm.example.com"
    volumes: ["./storage:/app/nocobase/storage"]
  redis:
    image: redis:7
    command: ["redis-server", "--maxmemory-policy", "noeviction"]
```
**Локальный проект** — запускайте лаунчер вместо `yarn start`:
```bash
REDIS_URL=redis://127.0.0.1:6379/0 node storage/multicore/supervisor/bin/nocobase-multicore.js
```
Затем откройте **Настройки → Многоядерный режим**, включите переключатель, выберите число воркеров (начните с числа ядер процессора) и нажмите «Применить». «Запустить проверку» запускает самопроверку кластера.

## Рабочие процессы, безопасность и удаление (FAQ)

**Продолжат ли работать рабочие процессы и триггеры (создание записи, расписание …)?** Да. Проверено: триггер коллекции + узел «создать запись» (асинхронный и синхронный), 150 и 600 выполнений: каждое выполнение создано и завершено ровно один раз, без дублей и потерь — так же, как в одном процессе. Триггеры по расписанию срабатывают один раз за такт (блокировка в Redis исключает двойной запуск). Плагины не трогают таблицы рабочих процессов и ваши данные.

**Что нашли тесты?** Реальную ошибку: адаптер worker id ставился слишком поздно, поэтому несколько воркеров могли получить одинаковый случайный id, и около 25 % выполнений триггеров терялись с ошибкой `id must be unique`. В этом выпуске исправлено (хук `afterAdd`), покрыто самопроверкой и `tests/workflow.js`.

**Какие ограничения?** (1) Очередь — *«хотя бы один раз»*: после сбоя посреди задачи она может выполниться снова, поэтому делайте действия рабочих процессов идемпотентными. (2) Синхронные рабочие процессы при очень высокой параллельности (сотни одновременных запросов) зависают и в штатном NocoBase, даже в одном процессе. (3) Включение плагинов из интерфейса в работающем кластере затрагивает один воркер — после этого перезапустите. (4) Изменения метаданных (новые коллекции/поля) доходят до всех воркеров примерно за 1 с.

**Если удалить плагины, сервер продолжит работать?** Да, ручное восстановление не нужно. Отключение/удаление любого из пяти плагинов сначала записывает `enabled:false` в конфиг (*страховка*), и супервизор возвращается к **одному обычному процессу**. Плагины не создают таблиц в БД и не меняют данные; оставшиеся ключи Redis безвредны и истекают сами. Проверено: сайт отвечал 200 на протяжении всего удаления, контейнер перезапустился штатно, сохранённые рабочие процессы продолжали срабатывать. Для чистого удаления используйте `./uninstall.sh --docker <контейнер>` (с `--purge` удаляется ещё и папка супервизора — делайте это только после возврата контейнера на штатный entrypoint).

**Рекомендации для боевого сервера:** сделайте резервную копию БД; сначала проверьте на копии; включайте в спокойный час; начните с 2–3 воркеров; следите за Redis (персистентность, мониторинг).

## Если что-то не работает

| Симптом | Причина / решение |
|---|---|
| Переключатель не включается | В сообщении указана причина: Redis не отвечает, плагин не включён или приложение запущено не через супервизор (шаг 2). |
| *Invalid sign-in origin* | Задайте `CORS_ORIGIN_WHITELIST` равным адресу, который открываете в браузере (штатная проверка NocoBase за прокси). |
| Полноэкранная ошибка «Script error for @rosal-nb/…» | Старая сборка без клиентской заглушки; используйте файлы из этого выпуска. |
| Плагин включён в интерфейсе, но адаптер не активен | Перезапустите контейнер (в кластере изменение увидел только один воркер). |
| В логе `… adapter not activated: REDIS_URL is not set` | Одиночный режим или нет Redis: так и должно быть, ничего не сломано. |

## Подробно о каждой части

### Супервизор (лаунчер)

_Запускает NocoBase несколькими процессами-воркерами на одном порту и меняет их число без простоя._

**Основа**

NocoBase community — это один процесс Node.js, то есть одно ядро процессора. Супервизор — маленький лаунчер (чистый Node.js, без импортов NocoBase)
на `node:cluster`. Это **главный** процесс: сам запросы не обслуживает, а запускает N **воркеров**, и каждый воркер — полноценное приложение NocoBase.
Операционная система раздаёт входящие соединения воркерам по кругу, поэтому нагрузка распределяется по нескольким ядрам.

**Функционал**

* Запускает 1..N воркеров (`bin/nocobase-multicore.js`); первый запуск слота 0 выполняет `start --quickstart` (установка/обновление БД), как стандартный образ.
* **Плавная замена** при смене режима или числа воркеров: стартует новый воркер, супервизор ждёт, пока он реально принимает запросы, затем старый выходит из раздачи соединений (`disconnect`), получает `SIGTERM` (30 с на завершение, затем `SIGKILL`). Пользователи ошибок не видят.
* Увеличение и уменьшение числа воркеров (сначала останавливаются старшие слоты).
* Перезапускает упавший воркер с нарастающей паузой (1 с → 30 с).
* Пишет `storage/multicore/status.json` (режим, воркеры, состояния) и читает `storage/multicore/config.json` (что сохранила страница настроек). Конфиг перечитывается по сообщению от воркера, по `SIGHUP` и каждые 10 с.
* Передаёт воркерам окружение: `MULTICORE_SUPERVISED=1`, `MULTICORE_MODE=cluster|single`, `MULTICORE_SLOT`, а в режиме кластера ещё `REDIS_URL`, `CACHE_DEFAULT_STORE=redis`, `CACHE_REDIS_URL`.
* `lib/worker-entry.js` выполняется в каждом воркере: запускает `initEnv()` консоли NocoBase (читает `.env`), откладывает открытие HTTP-порта до состояния приложения `running` (никто не получит «503 app is starting») и гарантирует завершение процесса после `SIGTERM`.

**Как устроено**

`docker/entrypoint.sh` (внутри пакета супервизора) подменяет **последнюю строку** штатного entrypoint официального образа (`yarn start --quickstart`) на запуск супервизора; всё остальное, что делает образ (nginx, клиентские файлы), сохраняется.
Если в новой версии образа эта строка изменится, скрипт остановится с понятным сообщением, а не запустит что-то неверное.

**Настройка**

| Настройка | По умолчанию | Смысл |
|---|---|---|
| `storage/multicore/config.json` | `{enabled:false, workers:1}` | Пишет страница настроек (или вручную). `enabled:false` = один обычный процесс. |
| `MULTICORE_MAX_WORKERS` | `min(ядра×2, 32)`, не меньше 2 | Верхняя граница числа воркеров. |
| `MULTICORE_QUICKSTART` | включено | `0` — не выполнять `--quickstart` при первом запуске. |
| `MULTICORE_EXIT_GRACE_MS` | `10000` | Сколько воркер может завершаться до `process.exit`. |
| `MULTICORE_APP_ENTRY` | авто | Путь к `@nocobase/app/lib/index.js`. |
| `MULTICORE_REDIS_PREFIX`, `MULTICORE_NAMESPACE` | `mcore`, имя БД | Префикс ключей Redis (несколько кластеров на одном Redis). |
| `MULTICORE_DEFER_LISTEN` | включено | `0` — открывать порт сразу (не рекомендуется). |
| `MULTICORE_STORAGE`, `MULTICORE_CONFIG` | `storage` | Где лежат файлы конфига и состояния. |

**Безопасность / удаление**

Выключение режима (или удаление плагинов) всегда возвращает супервизор к **одному обычному воркеру**, который работает как стандартный NocoBase.
Не удаляйте папку `storage/multicore/supervisor`, пока контейнер всё ещё запускается через неё.

**Как проверить**

```bash
docker exec <контейнер> cat storage/multicore/status.json     # нужный режим и состояние каждого воркера
docker logs <контейнер> 2>&1 | grep '\[multicore\]'           # события супервизора
```

### Плагин-менеджер — `@rosal-nb/plugin-multicore`

_Страница настроек с переключателем многоядерного режима, таблицей процессов и самопроверкой кластера._

**Основа**

Единственный плагин, с которым вы работаете напрямую. Добавляет в NocoBase страницу **Настройки → Многоядерный режим**, те же функции в виде API и следит за кластером.
Сам он ничего из функций NocoBase не переносит — это делают четыре плагина-адаптера.

**Функционал**

* **Переключатель и счётчик воркеров**, кнопка «Применить». Перед сохранением плагин проверяет, что Redis отвечает, что включены все четыре плагина-адаптера и что приложение действительно запущено под супервизором; иначе отказывает с понятной причиной.
* **Таблица процессов в реальном времени**: слот, PID, состояние, время работы, CPU %, память, лаг цикла событий, worker id (snowflake), хост. Данные — из heartbeat раз в 5 с через Redis (TTL 20 с).
* **Таблица адаптеров**: для каждого — состояние плагина (включён/выключен/нет) и действует ли адаптер в этом процессе на самом деле.
* **Самопроверка кластера** (кнопка «Запустить проверку» или `POST /api/multicore:selftest`): (1) сообщение pub/sub доходит до каждого воркера, (2) удерживаемая блокировка не пускает остальные воркеры, (3) 20 задач очереди обработаны ровно по одному разу, (4) у каждого воркера свой worker id.
* **API** (право `pm.multicore`, у root есть): `GET /api/multicore:status`, `POST /api/multicore:apply {"enabled":true,"workers":3}`, `POST /api/multicore:selftest`, `GET /api/multicore:whoami`.
* **Страховка**: если этот или любой плагин-адаптер отключают или удаляют при включённом кластере, плагин записывает `enabled:false` в конфиг и сообщает супервизору, тот возвращается к одному процессу — сайт не работает с «недоустановленным» кластером.

**Как устроено**

Сервер: регистрирует ресурс `multicore` и ACL-сниппет, общается с супервизором через Node IPC (`process.send`), пишет конфиг атомарно (временный файл + rename). Клиент: обычный клиентский плагин NocoBase (React + Ant Design), страница настроек; язык интерфейса — английский или русский по языку NocoBase.

**Настройка**

Собственных настроек нет. Управляемый файл — `storage/multicore/config.json`. Права: Настройки → Роли → *Настройки плагинов* → *Многоядерный режим*.

**Безопасность / удаление**

Отключение/удаление сначала выключает кластер (страховка выше). Плагин **не создаёт таблиц в БД** и не меняет данные.

**Как проверить**

```bash
curl -s -X POST $BASE/api/multicore:selftest -H "Authorization: Bearer $TOKEN"   # ожидается "ok": true
curl -s $BASE/api/multicore:status -H "Authorization: Bearer $TOKEN"
```

### Адаптер Pub/Sub — `@rosal-nb/plugin-pubsub-adapter-redis`

_Делает события видимыми для всех воркеров (Redis Pub/Sub)._

**Основа**

В NocoBase есть внутренняя шина событий (`app.pubSubManager`). «Из коробки» она работает в памяти: сообщение, опубликованное в одном процессе, доходит только до него.
При нескольких воркерах ломается всё, о чём нужно сообщить *всем* процессам. Плагин подключает к шине адаптер Redis Pub/Sub: сообщение одного воркера доходит до всех.

**Функционал**

Что ездит по этой шине в NocoBase:
* **изменения метаданных** — коллекция или поле, созданные в интерфейсе, появляются на каждом воркере (≈1 с, собственный debounce NocoBase);
* сообщения **сброса кэша**;
* **статусы рабочих процессов** — включение/выключение процесса регистрирует/снимает его триггер на каждом воркере;
* сообщения любых других плагинов, использующих `pubSubManager` / `syncMessageManager`.

**Как устроено**

Берутся два отдельных соединения Redis (соединение в режиме подписки не может публиковать) из штатного `redisConnectionManager` NocoBase (своего клиента Redis плагин не тащит). Каналы называются `mcore:<база>:ps:<канал>`. Ошибка в одном обработчике пишется в лог и не мешает остальным. Адаптер ставится в `beforeLoad`, подключается на `afterStart`.

**Настройка**

Работает только при `MULTICORE_MODE=cluster` и заданном `REDIS_URL`; иначе в логе `pub/sub adapter not activated`, и NocoBase использует свою штатную шину в памяти. Префикс Redis: `MULTICORE_REDIS_PREFIX` / `MULTICORE_NAMESPACE`.

**Безопасность / удаление**

В Redis ничего не хранится (каналы «отправил и забыл»). Отключение/удаление плагина сначала выключает кластер. В базу данных ничего не пишется.

**Как проверить**

Кнопка «Запустить проверку» на странице менеджера (pub/sub доходит до N из N воркеров), либо создайте коллекцию в интерфейсе и откройте её в другой вкладке браузера: она видна примерно через 1 с. Автоматизировано в `node tests/consistency.js`.

### Адаптер блокировок — `@rosal-nb/plugin-lock-adapter-redis`

_Блокировки работают между процессами (Redis `SET NX PX`)._

**Основа**

NocoBase использует блокировки (`app.lockManager`), чтобы два действия не выполнялись одновременно — например, обработка одного выполнения рабочего процесса,
восстановление незавершённых выполнений, срабатывание расписания. Штатная блокировка существует только внутри одного процесса. При нескольких воркерах два из них могли бы
решить, что держат одну и ту же блокировку. Плагин регистрирует адаптер блокировок на Redis и делает его адаптером по умолчанию.

**Функционал**

* Взаимное исключение **между процессами и серверами**: критическую секцию по одному ключу выполняет только один воркер.
* Та же семантика, что у штатного адаптера: `tryAcquire`, `acquire(key, ttl)` (ждёт), `runExclusive(key, fn, ttl)` (ждёт, выполняет, всегда освобождает).
* Пока критическая секция выполняется, блокировка **продлевается** каждые ttl/3, поэтому долгая задача её не теряет; если всё же потеряна — предупреждение в логе.
* Именно это защищает от **двойного срабатывания расписаний** и двойной обработки одного выполнения рабочего процесса.

**Как устроено**

`SET ключ токен NX PX ttl` — взять блокировку, Lua-скрипт для освобождения/продления **только при совпадении токена** (опоздавший воркер не сможет снять чужую блокировку).
Блокировка упавшего воркера сама истекает по TTL. Соединение — `redisConnectionManager` NocoBase.

**Настройка**

Работает только в режиме кластера с `REDIS_URL`. Регистрирует адаптер `redis` и назначает его `lockManager.options.defaultAdapter`; в одиночном режиме остаётся штатная блокировка. Ключи: `mcore:<база>:lock:*`.

**Безопасность / удаление**

Блокировки — короткоживущие ключи с TTL: после сбоя ничего не блокирует систему дольше TTL. В базу данных ничего не пишется.

**Как проверить**

«Запустить проверку»: блокировка, удерживаемая воркером страницы, не должна пускать остальные (`lockblocked = N-1`, `lockleak = 0`). Практический эффект проверяют `node tests/workflow.js` и рабочий процесс-расписание на 5 секунд (ровно один запуск за такт).

### Адаптер очереди — `@rosal-nb/plugin-queue-adapter-redis`

_Одна общая очередь задач для всех воркеров (Redis Streams): каждую задачу обрабатывает ровно один воркер._

**Основа**

NocoBase складывает фоновую работу в очередь событий (`app.eventQueue`): асинхронные выполнения рабочих процессов, часть уведомлений и задачи других плагинов.
Штатная очередь находится в памяти и принадлежит одному процессу. При нескольких воркерах каждый видел бы только свои задачи. Плагин заменяет её очередью на Redis Streams, общей для всех воркеров.

**Функционал**

* Каждое сообщение достаётся **ровно одному** воркеру во всём кластере (consumer group), поэтому нагрузка делится.
* После успеха сообщение подтверждается и удаляется; после ошибки публикуется заново со счётчиком повторов (как делает штатная очередь).
* **Восстановление после сбоя**: сообщение, оставшееся недообработанным у упавшего воркера, подхватывает другой (`XAUTOCLAIM`) через `timeout×2 + 5 с`.
* Доставка — **«хотя бы один раз»**: при редком сбое посреди задачи она может выполниться второй раз (проектируйте действия рабочих процессов так, чтобы повтор был безвреден).

**Как устроено**

`XADD` — публикация, `XREADGROUP` (группа `nb`, потребитель `<pid>-<случайное>`) — получение, `XACK` + `XDEL` при успехе; длина потока ограничена 100 000 записей; интервал опроса по умолчанию 250 мс. Ключ потока `mcore:<база>:q:<канал>`.

**Настройка**

Работает только в режиме кластера с `REDIS_URL`. Redis не должен вытеснять ключи (`maxmemory-policy noeviction`), чтобы задачи очереди не пропадали.

**Безопасность / удаление**

Незавершённые задачи лежат в Redis. При выключении кластера вступает в силу штатная очередь в памяти; задачи, ещё ожидавшие в потоке Redis в этот момент, не переносятся — выключайте в спокойный момент (менеджер и `uninstall.sh` дожидаются завершения текущей работы воркеров; поставленные в очередь выполнения рабочих процессов NocoBase находит заново в базе при собственном восстановлении на старте).

**Как проверить**

«Запустить проверку»: 20 тестовых задач → 20 обработано, 0 дубликатов, распределены по воркерам. `node tests/workflow.js 600 24 0` пропускает через очередь 600 настоящих выполнений рабочих процессов: ожидается 600/600.

### Выдача worker id — `@rosal-nb/plugin-worker-id-allocator-redis`

_Даёт каждому процессу свой id, чтобы два воркера не создали запись с одинаковым id._

**Основа**

NocoBase генерирует первичные ключи многих таблиц (выполнения рабочих процессов, задания, уведомления ...) алгоритмом **snowflake**: время + **worker id** (0–31) + счётчик. «Из коробки»
каждый процесс выбирает worker id **случайно**. Для одного процесса это нормально; при нескольких воркерах два из них могут выбрать одно число и создать одинаковые id в одну и ту же
миллисекунду — база отвечает `id must be unique`, и запись (например, выполнение рабочего процесса) теряется. Плагин выдаёт уникальные id.

**Функционал**

* Каждый процесс **арендует** свободный id 0–31 в Redis (`SET NX PX 30 с`), продлевает аренду каждые 10 с и держит её, пока жив процесс.
* Упавший процесс освобождает id автоматически через 30 с. Одновременно может работать не более 32 процессов (по умолчанию супервизор допускает не более 32 воркеров).
* Страница менеджера показывает id каждого воркера, а самопроверка падает, если у двух воркеров одинаковый id.

**Как устроено**

Ядро запрашивает id сразу после инициализации плагинов, **до** вызова `beforeLoad` плагинов, поэтому адаптер ставится в `afterAdd()`. (В предыдущей сборке стоял `beforeLoad` — это было слишком поздно, и
случайные id проходили; ошибку нашёл тест рабочих процессов, в этом выпуске она исправлена.) `release()` намеренно ничего не делает: ядро вызывает его при каждой *перезагрузке* приложения, пока процесс продолжает использовать id.

**Настройка**

Работает только в режиме кластера с `REDIS_URL`. Ключи: `mcore:<база>:wid:<0-31>`.

**Безопасность / удаление**

Уже сохранённые в вашей базе id не затрагиваются; плагин влияет только на новые. Отключение сначала выключает кластер.

**Как проверить**

```bash
curl -s -X POST $BASE/api/multicore:selftest -H "Authorization: Bearer $TOKEN"   # checks.workerIds.ok должно быть true
docker exec <redis> redis-cli --scan --pattern '*:wid:*'                           # по ключу на каждый работающий воркер
```
