# Архитектура

## Почему не `pm2 -i` / `CLUSTER_MODE`
Штатный `nocobase start` умеет запускать pm2 с несколькими инстансами, но все адаптеры по умолчанию внутрипроцессные: события, блокировки и очередь не пересекают границу процесса, идентификаторы записей могут совпасть. Вместо этого здесь есть управляемый запуск (переключатель в UI) и общие адаптеры на Redis.

## Схема
```
Браузер ─► порт 80/13000 ─► nginx (образ) ─► порт приложения
                                              │
                    nocobase-multicore (primary, node:cluster)
                      ├─ slot 0 ─ NocoBase ─┐
                      ├─ slot 1 ─ NocoBase ─┤  общий слушающий сокет, round-robin
                      └─ slot N ─ NocoBase ─┘
                                 │ Redis: pub/sub · блокировки · очередь (Streams)
                                 │        worker id (аренды) · кэш · heartbeat воркеров
                                 ▼
                              PostgreSQL / MySQL (общая БД)
```

## Лаунчер (`packages/supervisor`)
* **primary**-процесс `node:cluster`. Не загружает код NocoBase, поэтому не может «упасть» вместе с приложением.
* `worker-entry.js` — вход воркера: выполняет `initEnv()` из CLI NocoBase (читает `.env`, выставляет `APP_PACKAGE_ROOT` и др.) и загружает `@nocobase/app/lib/index.js` в этом же процессе → воркер делит слушающий порт лаунчера. Без этого шага приложение падает с `Cannot find @nocobase/preset-nocobase package.json`.
* Конфиг `storage/multicore/config.json`; переключение — «плавная замена»: поднимается новый воркер (временный слот 1000+n), ждётся событие `listening`, старый **сначала отключается от раздачи соединений** (`worker.disconnect()`), через 1.5 с получает SIGTERM, через 30 с — SIGKILL. Уменьшение числа воркеров выполняется до замены, чтобы не поднимать воркер, который тут же погасят.
* **Воркер открывает порт только когда приложение готово.** Шлюз NocoBase открывает HTTP-порт раньше, чем загружает приложение, и до этого отвечает 503. В кластере primary уже направлял бы на такой воркер живой трафик. Поэтому `worker-entry.js` откладывает первый TCP `listen()` до статуса приложения `running` (`AppSupervisor.getAppStatus('main')`); отключается `MULTICORE_DEFER_LISTEN=0`.
* Событие `listening` кластера приходит и для unix-сокета IPC шлюза (порт `-1`), поэтому лаунчер считает воркер готовым только по событию с `port > 0`.
* Воркер завершается сам: после SIGTERM NocoBase останавливает приложение, но процесс остаётся (открытые дескрипторы), поэтому `worker-entry.js` ставит таймер `process.exit(0)` (10 с).
* **Балансировщик «наименее занятый»** (`lib/balancer.js`, включён по умолчанию; `MULTICORE_BALANCER=off` возвращает общий порт). Публичный порт держит лаунчер, каждый воркер слушает свой приватный loopback-порт. Каждый HTTP-*запрос* уходит воркеру с наименьшей оценкой нагрузки: запросы в работе + лаг цикла событий / 100 мс (не больше 10; лаг меньше 50 мс — обычное дрожание таймера и считается нулём) + 1000, пока воркер 1,5 с не присылал heartbeat. Воркеры шлют heartbeat по IPC каждые 500 мс вместе с опозданием своего таймера, поэтому воркер, занятый одним тяжёлым запросом, получает меньше новых задолго до того, как считается зависшим.
  *Правила учёта* (каждое до 0.2.0 было реальной ошибкой): запрос числится «в работе» ровно на одном воркере и снимается ровно один раз за попытку; запрос, клиент которого ушёл, отменяется у воркера и **никогда не повторяется** (повтор и выполнял запрос дважды, и навсегда оставлял «+1 в работе» у второго воркера — в итоге весь трафик уходил на один воркер); запрос повторяется, только если его тело можно отправить заново (тела нет или оно ≤ 1 МиБ и сохранено балансировщиком) и первый воркер точно его не обработал — отказ в соединении, любой сбой чтения (`GET`/`HEAD`/`OPTIONS`) или сброс *повторно используемого* keep-alive-соединения до первого байта ответа при живом воркере.
  *Keep-alive:* балансировщик держит соединения с воркерами и закрывает простаивающие через 8 с; `worker-entry.js` поднимает `keepAliveTimeout` HTTP-сервера воркера до 10 минут. Со стандартными 5 с воркер, чей цикл событий был занят дольше, при пробуждении первым делом выполнял просроченные таймеры keep-alive и рвал соединения, в которых уже лежали непрочитанные запросы (клиент видел «Bad gateway»).
* Упавший воркер перезапускается с задержкой 1 → 2 → … → 30 с; задержка сбрасывается после минуты стабильной работы. Причина завершения определяется (`oom` = SIGABRT/134, `killed` = SIGKILL/137, `crash`, `signal`, `error`) и пишется в журнал.
* **Ручной перезапуск** слота (или всех по очереди) — та же плавная замена; если замена не дошла до `listening`, она удаляется, а старый воркер продолжает работать.
* **Лимит кучи**: `heapMb` из конфига передаётся как `--max-old-space-size` в `execArgv` (важнее `NODE_OPTIONS`); при изменении значения слоты считаются устаревшими и заменяются по одному.
* **Журнал**: `Supervisor.event()` хранит последние 200 событий в памяти (отдаются вместе со статусом) и дописывает их в `storage/multicore/events.log`. Heartbeat, пришедший через 5 с и более после предыдущего, записывается как `stall` с длительностью.
* **Snowflake-id живых воркеров**: плагин worker-id сообщает арендованный id по IPC (`type:'wid'`); лаунчер передаёт id живых воркеров каждому новому в `MULTICORE_WID_AVOID`.
* Слоты >0 и заменяющие воркеры получают уникальный `SOCKET_PATH` (сокет IPC шлюза NocoBase принадлежит одному процессу).
* IPC: `{cmd:'multicore', type:'apply'|'status'|'restart'|'hb'|'wid', reqId}` ↔ `apply:ack` / `status:res` / `restart:ack` (`hb` несёт `lag`, `restart` — `slot`). Запасные каналы: `SIGHUP`, опрос файла раз в 10 с, `status.json`.

## Адаптеры
Каждый плагин включается только при `MULTICORE_MODE=cluster` и заданном `REDIS_URL`; иначе пишет в лог причину и ничего не меняет.

| Плагин | Точка расширения NocoBase | Реализация |
|---|---|---|
| pubsub | `app.pubSubManager.setAdapter` | Отдельные pub/sub-подключения; канал `${prefix}:ps:${channel}`; подключение на `afterStart`. |
| lock | `app.lockManager.registerAdapter('redis')` + `options.defaultAdapter` | `SET NX PX`, Lua для сравнения-и-удаления/продления, продление по таймеру, `LockAcquireError` как у штатного адаптера. |
| queue | `app.eventQueue.setAdapter` | Redis Streams, группа `nb`, `XREADGROUP` на отдельном подключении, `XACK`+`XDEL`, повтор публикацией с `retried+1`, `MAXLEN ~100000`. Пока обработчик работает, его воркер каждые 10 с обновляет сообщение (`XCLAIM … JUSTID` на себя); сообщения, которые никто не обновлял 90 с, принадлежат мёртвому воркеру и забираются через `XAUTOCLAIM`. (До 0.2.0 любую задачу дольше 35 с забирал другой воркер и запускал второй раз.) |
| worker-id | `app.workerIdAllocator.setAdapter` | 32 аренды `${prefix}:wid:${id}` (TTL 60 с, продление раз в 10 с; потерянная аренда возвращается, иначе воркер под супервизором завершается и перезапускается); синглтон `globalThis.__mcoreWorkerId` с `rebind(app)` — переживает перезагрузку приложения. Id из `MULTICORE_WID_AVOID` (их держат живые соседние воркеры) не занимаются, даже если их аренда истекла. |
| кэш | переменные `CACHE_DEFAULT_STORE=redis`, `CACHE_REDIS_URL` | Выставляет лаунчер для воркеров кластера. |

Префикс ключей: `${MULTICORE_REDIS_PREFIX||'mcore'}:${MULTICORE_NAMESPACE||DB_DATABASE||'nocobase'}`.

## Менеджер (`@nb-multicore/plugin-multicore`)
* Ресурс `multicore`: `status`, `apply`, `selftest`, `whoami`, `restart`, `connections`; ACL-сниппет `pm.multicore`.
* `apply` проверяет Redis, что все четыре адаптера включены и что приложение запущено под лаунчером; пишет конфиг атомарно (tmp + rename) и сообщает лаунчеру.
* Heartbeat: каждый воркер раз в 5 с пишет в `${prefix}:workers:${pid}` (TTL 20 с) pid, слот, CPU %, RSS, кучу и её лимит, p99 лага цикла событий, число WebSocket-клиентов и вошедших пользователей; в `${prefix}:conn:${pid}` — список `[userId, вкладок, с какого времени, ip]` своих WebSocket-клиентов (из `Gateway.getInstance().wsServer.webSocketClients`, тег `userId#<id>` ставит плагин авторизации); и добавляет себя в упорядоченное множество `${prefix}:workers:index` (список живых воркеров без `SCAN` по всем ключам). Всё одним конвейером.
* Таблица воркеров строится по списку слотов лаунчера (он знает точно: воркер с занятым циклом событий heartbeat не шлёт, но существует) и дополняется данными heartbeat из Redis и счётчиками балансировщика.
* `connections` объединяет списки всех воркеров (или одного слота), подставляет имена из коллекции `users` (кэш 60 с) и возвращает пользователей с числом вкладок по воркерам.
* `selftest`: pub/sub-пинг должен дойти до всех воркеров; блокировка, взятая инициатором, должна блокировать остальных (и не «протекать»); 20 сообщений очереди должны обработаться ровно по разу.
* Клиент: страница настроек (ru/en/zh), опрос статуса каждые 4 с (в фоновой вкладке браузера опрос приостанавливается).
