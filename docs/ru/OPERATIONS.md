# Эксплуатация

## Требования
* NocoBase 2.x (проверено 2.2.33), Node.js 20+ внутри образа.
* Redis 6+ (проверено 7.4) c `maxmemory-policy noeviction` или без вытеснения ключей `mcore:*`.
* PostgreSQL/MySQL — как для обычного NocoBase. Соединений с БД понадобится ×N воркеров: проверьте `max_connections`.

## Установка и удаление (скрипты)
Из распакованного бандла `nocobase-multicore-bundle-<версия>.tgz` (или из `scripts/` репозитория):
```bash
./install.sh --docker <контейнер> --restart     # либо: ./install.sh --local /путь/к/проекту
./uninstall.sh --docker <контейнер>             # --purge дополнительно удаляет папку супервизора
```
`install.sh` идемпотентен: копирует плагины в `storage/plugins/@nb-multicore/<имя>/`, супервизор в `storage/multicore/supervisor/`, выполняет `pm add` + `pm enable`. Опции: `--no-enable`, `--from <папка с tgz>`, `--restart`.
`uninstall.sh`: (1) записывает `enabled:false` и ждёт, пока супервизор вернётся к одному процессу; (2) `pm disable`; (3) `pm remove` и удаление `storage/plugins/@nb-multicore`; (4) папку `storage/multicore/supervisor` **оставляет**, пока контейнер запускается через неё (удаляйте с `--purge` только после возврата на штатный entrypoint).

## Файлы лаунчера
Лаунчер лежит в `storage/multicore/supervisor/` (его кладёт `install.sh`; в репозитории — `packages/supervisor`). Точка входа: `node storage/multicore/supervisor/bin/nocobase-multicore.js`, запускать из корня проекта NocoBase (в образе `/app/nocobase`).

## Docker (официальный образ `nocobase/nocobase`)
Образ запускает приложение последней строкой своего `/app/docker-entrypoint.sh` (`yarn start --quickstart`). Скрипт `packages/supervisor/docker/entrypoint.sh` берёт штатный entrypoint, заменяет только эту строку на запуск лаунчера и выполняет его — остальная подготовка образа (nginx, клиентские файлы) сохраняется. Если в новой версии образа строка изменилась, скрипт остановится с понятной ошибкой.

В сервис `app` нужно добавить:
```yaml
entrypoint: ["/bin/sh", "/app/nocobase/storage/multicore/supervisor/docker/entrypoint.sh"]
environment:
  REDIS_URL: redis://redis:6379/0
  # CORS_ORIGIN_WHITELIST: "https://ваш-адрес"   # если «Invalid sign-in origin» за прокси
```
Готовый пример — `docker/docker-compose.example.yml` (там лаунчер примонтирован как `/multicore`).

## Не Docker
Из корня проекта: `node storage/multicore/supervisor/bin/nocobase-multicore.js` вместо `yarn start`. Переменные окружения те же, что у обычного запуска (`.env` читается воркерами так же, как это делает `nocobase start`).

## Подключение плагинов вручную
```bash
cd /app/nocobase   # корень проекта в контейнере
# распакуйте каждый nb-multicore-plugin-<имя>-<версия>.tgz в storage/plugins/@nb-multicore/plugin-<имя>/
yarn nocobase postinstall   # в NocoBase 2.x `pm add` для уже лежащих в storage/plugins плагинов ничего не делает
yarn nocobase pm enable @nb-multicore/plugin-pubsub-adapter-redis @nb-multicore/plugin-lock-adapter-redis \
  @nb-multicore/plugin-queue-adapter-redis @nb-multicore/plugin-worker-id-allocator-redis @nb-multicore/plugin-multicore
```
Папки плагинов лежат в `storage/plugins/@nb-multicore/<имя>/`. Либо загрузите `.tgz` из релиза через «Менеджер плагинов → Добавить → Загрузить». **Включение/загрузка из интерфейса в работающем кластере затрагивает только обработавший запрос воркер — после этого перезапустите контейнер.**

## Рабочие процессы и удаление плагинов
* Триггеры и рабочие процессы работают как в одном процессе (тесты `tests/workflow.js`: 150/150, 600/600, синхронный 40/40, без дублей и потерь). Плагины не создают таблиц и не меняют данные.
* Удаление/отключение любого плагина сначала выключает кластер (страховка `turnOffClusterMode`, пишет `enabled:false`), супервизор возвращается к одному процессу; ручное восстановление NocoBase не требуется.
* Очередь — «хотя бы один раз»: действия рабочих процессов должны быть идемпотентными.

## Чек-лист для боевого сервера
1. Резервная копия БД и `storage/`.
2. Сначала проверить на копии/тестовом сервере (`tests/workflow.js`, самопроверка).
3. Redis: `maxmemory-policy noeviction`, мониторинг; `max_connections` БД ≥ воркеры × пул.
4. Включать в тихий час, начать с 2–3 воркеров.
5. Откат: переключатель выключить в UI (или `{"enabled": false}` в `config.json`), либо `uninstall.sh`.

## Управление
* UI: Настройки → Многоядерный режим.
* API (нужна роль с правом `pm.multicore`, у root оно есть):
  * `POST /api/multicore:apply {"enabled":true,"workers":2,"affinity":"off","heapMb":0}` (`affinity`: `off` | `token` | `ip`; `heapMb` — лимит кучи воркера, `0` — не задавать);
  * `GET /api/multicore:status`, `POST /api/multicore:selftest`, `GET /api/multicore:whoami`;
  * `POST /api/multicore:restart {"slot": 1}` или `{"slot": "all"}` — перезапуск одного воркера / всех по очереди без простоя;
  * `GET /api/multicore:connections?slot=1` — кто подключён к этому воркеру (без `slot` — ко всему кластеру, `&summary=1` — только итоги).
* Файлы: `storage/multicore/config.json` (настройки), `storage/multicore/status.json` (состояние лаунчера, счётчики балансировщика, хвост журнала), `storage/multicore/events.log` (журнал, по строке JSON на событие; при размере больше 512 КБ обрезается до последних 200 записей). Лаунчер перечитывает конфиг по сообщению от воркера, по `SIGHUP` и раз в 10 секунд.
* Откат без UI: поставьте `{"enabled": false}` в `config.json` (или удалите файл) — лаунчер вернёт один процесс.

## Переменные окружения
| Переменная | По умолчанию | Смысл |
|---|---|---|
| `REDIS_URL` | — | Redis для кластера (обязательна для включения). |
| `MULTICORE_APP_ENTRY` | поиск `@nocobase/app` | Путь к `@nocobase/app/lib/index.js`. |
| `MULTICORE_MAX_WORKERS` | `min(ядра×2, 32)`, не меньше 2 | Верхняя граница числа воркеров. |
| `MULTICORE_QUICKSTART` | включён | `0` — не выполнять `start --quickstart` при первом старте. |
| `MULTICORE_EXIT_GRACE_MS` | `10000` | Сколько воркер может завершаться до `process.exit`. |
| `MULTICORE_KEEPALIVE_MS` | `600000` | Сколько воркер держит простаивающее соединение от балансировщика. Балансировщик сам закрывает простаивающие соединения через 8 с; воркер не должен делать это первым. |
| `MULTICORE_BALANCER` | включён | `off` — обычный режим с общим портом вместо балансировщика. |
| `MULTICORE_REDIS_PREFIX` / `MULTICORE_NAMESPACE` | `mcore` / имя БД | Префикс ключей Redis; разные кластеры на одном Redis. |
| `MULTICORE_STORAGE` / `MULTICORE_CONFIG` | `storage` | Где лежат `config.json`, `status.json` и `events.log`. |

## Сколько воркеров ставить
Не больше числа физических ядер (минус ядра под БД и Redis, если они на том же сервере). Каждый воркер — полноценный процесс NocoBase: примерно 350–400 МБ памяти в простое (под нагрузкой больше, см. таблицу воркеров) и свой пул соединений с БД. Во время плавного перезапуска некоторое время работает один лишний воркер, поэтому `(воркеры + 1) × DB_POOL_MAX` должно быть меньше `max_connections` базы — страница настроек об этом предупреждает.

## Диагностика
* **Журнал событий** (страница настроек, `storage/multicore/events.log`) — смотреть в первую очередь: завершения воркеров с причиной, зависания, перезапуски, ответы «Bad gateway».
* `docker logs <контейнер> | grep '\[multicore\]'` — те же события лаунчера обычными строками лога.
* Страница показывает по каждому воркеру: состояние, CPU, память и лимит кучи, лаг цикла событий, запросы в работе / обработано / в секунду, среднее время ответа, открытые вкладки и пользователей, падения и зависания.
* Самотест: pub/sub доходит до всех, блокировка исключает другой процесс, 20 задач очереди обработаны по одному разу.

## Перезапуск воркера вручную
*Настройки → Многоядерный режим → Воркеры → «Перезапустить»* (или «Перезапустить все по очереди»). Лаунчер запускает замену, ждёт, пока она начнёт обслуживать запросы, затем убирает старый воркер из балансировки, даёт ему завершить запросы (до 30 с) и останавливает — пользователи ничего не замечают, только открытые вкладки переподключают WebSocket. Если замена не запустилась, старый воркер продолжает работать, а в журнале появляется запись об этом. Пригодится после включения плагина из интерфейса (изменение увидел только один воркер) или чтобы освободить память разросшегося воркера.

## Лимит памяти воркера
Каждый воркер — отдельный процесс Node.js со своим лимитом кучи JavaScript. «Лимит памяти воркера» (`heapMb` в `config.json`) передаёт воркерам `--max-old-space-size=<МБ>`; это значение важнее указанного в `NODE_OPTIONS`. Пусто или `0` — остаётся значение Node по умолчанию (или из `NODE_OPTIONS`). Изменение применяется плавной заменой. Воркер, упёршийся в лимит, завершается самим Node («нехватка памяти» в журнале) и запускается заново, а запросы, которые он обслуживал, получают ошибку — поэтому не ставьте лимит ниже того, что требовалось NocoBase в одном процессе на тех же данных (в таблице видно «использовано кучи (лимит)» по каждому воркеру). Лимиты — это потолок, а не резерв: их сумма может превышать память сервера, пока воркеры не заполняют её все одновременно.

## Журнал событий
*Настройки → Многоядерный режим → Журнал событий* и файл `storage/multicore/events.log`. События: `boot`, `reconcile` (конфигурация применена), `worker-ready`, `worker-exit` (с причиной `reason`: `oom` — достигнут лимит кучи; `killed` — SIGKILL, обычно это OOM-killer ядра; `error` + код выхода; `crash`; `signal`), `stall` (воркер не отвечал на heartbeat 5 с и дольше, с длительностью), `restart-requested` / `restarted`, `bad-gateway` (ответы 502 балансировщика, сгруппированные по 5 с, с кодами ошибок), `failed`, `shutdown`.

## Цепочка прокси в официальном образе
`обратный прокси (Caddy и т. п.) → nginx внутри образа NocoBase (порт 80) → балансировщик (APP_PORT, 13000) → воркер`. Что проверить, если сайт «иногда открывается медленно»:
* nginx в образе работает с настройками по умолчанию (`worker_processes auto`, `worker_connections 1024`). Каждая открытая вкладка держит WebSocket, то есть два соединения nginx; нескольким тысячам открытых вкладок нужен больший `worker_connections`.
* nginx сжимает (gzip) только ответы на запросы, пришедшие не через другой прокси (`gzip_proxied` по умолчанию выключен). За Caddy включите сжатие в нём (`encode zstd gzip`), иначе большие JSON-списки идут несжатыми.
* Журнал доступа nginx `/var/log/nginx/nocobase.log` внутри контейнера не ротируется и растёт до пересоздания контейнера.
* Один огромный синхронный запрос по-прежнему целиком занимает один воркер (JavaScript однопоточен). Такие моменты видны в журнале как `stall` с длительностью; лечится уменьшением размера страницы и числа подгружаемых связей в тяжёлом блоке.
